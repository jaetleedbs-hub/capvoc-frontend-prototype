# AI 화면 개발 요청문

> **읽는 이** — PPTX 로 화면을 설계하고 Claude Code 나 Cursor 에게 화면을 맡기는 **개발자.**
> 아래 요청문을 복사해 `{ }` 만 채우고, **캡처한 그림을 함께 붙여** 보낸다.
> `@frontend/docs/…` 는 두 도구 모두에서 그 파일을 읽히는 표기다.

## 흐름

```
① 그림 + 요청문 A  ─→  AI 가 SPEC.md(화면기능정의)를 쓰고 «멈춘다»
② SPEC.md 검토 · §8 「확인 필요」에 답한다
③ 요청문 B          ─→  AI 가 index.js · 메뉴 SQL 을 쓰고, 빌드하고, 띄워서 본다
④ 화면을 직접 열어 그림과 나란히 본다
```

**왜 두 번에 나누나** — 그림에는 늘 «읽히지 않는 것»이 있다(코드 목록, 필수 여부, 없는 API).
한 번에 끝까지 시키면 AI 가 그것을 그럴듯하게 **지어내고**, 지어낸 곳은 돌아가는 것처럼 보여서 가장 늦게 드러난다.
SPEC 에서 한 번 멈추면 그 자리가 「확인 필요」로 드러난다.

## 그림을 잘 주는 법

- **슬라이드 전체 한 장 + 복잡한 영역 확대 한 장.** 작은 글자는 확대본이 없으면 잘못 읽는다.
- 슬라이드의 **설명 글(주석·말풍선·기능 설명 표)은 그림이 아니라 글로** 붙여 넣는다. 그림 속 글자보다 정확하다.
- 화면 ID 는 반드시 적는다. 없으면 AI 가 묻는다(지어내지 않게 해 두었다).
- 같은 화면의 팝업은 **따로 요청**한다(팝업도 화면 하나다).

## A. 새 화면 — 1단계: 화면기능정의

```text
첨부한 그림은 PPTX 로 설계한 화면이다. 이 화면을 이 저장소의 표준대로 만들려고 한다.
이번에는 «화면기능정의(SPEC.md)만» 쓰고 멈춰라. index.js 는 아직 쓰지 마라.

먼저 읽을 것:
@frontend/docs/screen-standard.md
@frontend/docs/spec-template.md
@frontend/docs/design-standard.md
@frontend/docs/component-reference.md

화면 정보:
- 화면 ID: {SMP0010}
- 화면명: {샘플관리}
- 메뉴 위치: {샘플 > 샘플관리}  (새 메뉴 폴더가 필요하면 그것도 SPEC §7 에)
- 열리는 방식: {본문 탭 | 팝업 800x600}
- 백엔드 API: {없음 — 계획값으로 적어라 | 있음 — backend 에서 찾아 경로를 적어라}
- 설계서: {파일명.pptx} 슬라이드 {n}
- 슬라이드 설명 글:
  {여기에 붙여 넣는다 — 없으면 "없음"}

할 일:
1. 그림을 영역으로 나누고 화면 패턴(L1~L6)을 정하라. (screen-standard §4)
2. 요소마다 판독표(§4-2)로 부품을 고르고, 명명 규칙(§3)으로 ID 를 지어라.
3. spec-template 대로 frontend/src/containers/{smp}/{SMP0010}/SPEC.md 를 써라.
4. 그림에서 읽을 수 없거나, 표준과 다르거나, 둘 이상으로 읽히는 것은
   전부 §8 「확인 필요」에 질문으로 적어라. 그럴듯한 값으로 채우지 마라.
5. 끝나면 §8 의 질문만 나에게 다시 보여 주고 멈춰라.
```

## B. 새 화면 — 2단계: 퍼블리싱

```text
@frontend/src/containers/{smp}/{SMP0010}/SPEC.md 를 검토했다. §8 에 답을 적었다.
{추가로 바꿀 것이 있으면 여기에}

이제 화면을 만들어라.

1. SPEC.md 의 §8 답을 위 절들에 반영하라.
2. screen-standard §5-1 골격으로 index.js 를 써라. 화면 패턴은 SPEC §1 대로.
   - 보이는 글자는 전부 TEXT 로. 한글 리터럴을 render 에 두지 마라.
   - API 상태가 미구현이면 componentDidMount 의 자동 조회를 빼라.
3. screen-standard §6 대로 메뉴 등록 마이그레이션을 만들어라. 번호는 npm run db:status 로 확인.
4. cd frontend && yarn build 로 컴파일을 확인하라.
5. 화면을 띄워 그림과 나란히 보고, screen-standard §8 체크리스트를 하나씩 확인해 결과를 보고하라.
   띄울 수 없으면 «못 띄웠다»고 말하고, 내가 무엇을 확인하면 되는지 적어라.
6. 띄운 화면을 screen-standard §2 대로 찍어 SPEC.md 옆에 screen.png 로 두고 §0 에 걸어라.
```

## C. 간단한 화면 — 한 번에

조회만 하는 화면처럼 «읽히지 않는 것»이 거의 없을 때.

```text
첨부한 그림대로 화면을 만들어라.
@frontend/docs/screen-standard.md 의 §1 순서를 따르되, SPEC.md §8 「확인 필요」가 비어 있으면
멈추지 말고 퍼블리싱(index.js · 메뉴 SQL · 빌드 · 띄워서 확인 · screen.png)까지 이어서 해라.
§8 에 하나라도 있으면 거기서 멈추고 물어라.

- 화면 ID: {SMP0020}
- 화면명: {…}
- 메뉴 위치: {…}
- 백엔드 API: {없음 | 있음}
```

## D. 설계가 바뀌었을 때

```text
{SMP0010} 화면의 설계가 바뀌었다. 첨부한 그림이 새 설계다.
@frontend/src/containers/{smp}/{SMP0010}/SPEC.md
@frontend/src/containers/{smp}/{SMP0010}/index.js

1. 지금 SPEC 과 새 그림의 차이를 표로 보여라 (추가 · 삭제 · 변경).
2. SPEC.md 를 먼저 고치고 §0 의 판·날짜를 올려라. 새로 생긴 모호함은 §8 에.
3. §8 이 비어 있으면 index.js 를 고치고, 바꾼 줄만이 아니라 화면 전체를 띄워 확인하라.
4. 배치가 바뀌었으면 screen.png 를 다시 찍어라.
```

## E. 백엔드 API 가 생겼을 때

```text
{SMP0010} 의 백엔드 API 가 생겼다.
@frontend/src/containers/{smp}/{SMP0010}/SPEC.md

1. backend 에서 실제 컨트롤러 경로와 요청·응답 DTO 필드를 찾아 SPEC §4 와 대조하라.
   다르면 차이를 먼저 보여라 — 화면에 맞추려고 API 를 지어내지 마라.
2. SPEC §4 의 API 상태를 「구현」으로, 경로·필드를 실제 값으로 고쳐라.
3. index.js 의 API 맵·요청 필드를 맞추고, 자동 조회가 필요하면 componentDidMount 에 넣어라.
4. 띄워서 조회 → 상세 → 저장 → 삭제를 실제로 눌러 보고 결과를 보고하라.
```

## 받은 결과를 볼 때

- [ ] `SPEC.md` 의 §3 ID 가 `{접두어}[Srch]{필드}` 꼴인가 — `iptSrchUserNm`, `selUseYn`
- [ ] 버튼 색이 그림이 아니라 표준을 따랐나 — 조회·저장·선택만 파랑
- [ ] 그림에 없는 칸·버튼이 생기지 않았나
- [ ] 화면을 열었을 때 오류창이 뜨지 않나 (API 가 없으면 자동 조회가 빠져 있어야 한다)
- [ ] AI 가 「띄워서 봤다」고 했나, 「빌드만 했다」고 했나
- [ ] 화면 폴더에 `screen.png` 가 있고, 지금 화면과 같은가
